# Overview

Tabular modeling starts with data arranged in a table—often a CSV—and uses some of its columns to predict another. A customer profile, for example, might contain everything we know about a customer. Given those columns, how likely is that person to stop doing business with us?

That immediately gives us a practical problem. A model trains on tensors of numbers, but a table may contain store names, product categories, dates, and other values that aren't naturally numerical. How the heck do we turn those values into something the model can learn from?

This is where _embeddings_ become important.

# Categorical Embeddings

Before digging into embeddings, we need to distinguish between two kinds of variables that commonly appear in tabular datasets:

1. **Continuous variables** contain numerical measurements, such as age or temperature. Their numerical relationships carry meaning, so they can usually be passed to a model as numbers.
2. **Categorical variables** contain a fixed set of discrete values, such as a product type or state. Arithmetic on these values has no useful meaning.

A categorical value can still look like a number. Consider a `movie_id`. The integer is only a label from a particular catalog, not a measurement: "Die Hard" might be `movie_id: 1` in one system and `movie_id: 100` in another. Multiplying either ID by two tells us nothing about the movie.

The model still needs a numerical input, but we need a representation that treats the ID as a category rather than a quantity.

## A Brief History

Kaggle's [Rossmann Store Sales competition](https://www.kaggle.com/competitions/rossmann-store-sales) ran from September 30 to December 14, 2015. Competitors had to forecast six weeks of daily sales for 1,115 Rossmann stores in Germany using information about promotions, competitors, holidays, seasonality, location, and more. Rossmann hoped that better forecasts would help store managers build better staff schedules.

Cheng Guo and Felix Berkhahn's model placed third. They later described their approach in ["Entity Embeddings of Categorical Variables"](https://arxiv.org/abs/1604.06737). Their results suggested that learned embeddings give neural networks a compact way to represent categorical variables—particularly variables with many possible values—and can help the model generalize when examples are sparse.

To see why, consider a `state` category. Germany has 16 federal states, although the Rossmann paper's dataset contained only 12 state categories. One option is to represent each state with a one-hot vector:

```python
berlin = [1, 0, 0, ..., 0]
hamburg = [0, 1, 0, ..., 0]
hessen = [0, 0, 1, ..., 0]
```

This representation can distinguish Berlin from Hamburg, but it doesn't express any relationship between them. Every pair of distinct one-hot vectors is equally far apart. A downstream model can still learn an effect for each category, but the vectors themselves provide no notion of similarity.

An embedding replaces each sparse one-hot vector with a smaller, dense vector whose values can be learned. Mathematically, looking up an embedding is equivalent to multiplying a one-hot vector by a learned weight matrix—the same operation a linear layer would perform. The lookup is more practical because it selects the relevant row directly instead of constructing the sparse one-hot vector.

Like the other weights in a neural network, an embedding table usually begins with random values. Each category selects one row from that table. The state embeddings might initially look like this:

```text
                    dim1    dim2    dim3

Bavaria             0.18   -0.42    0.71
Baden-Württemberg  -0.55    0.13   -0.21
Berlin               0.82    0.07    0.34
Hamburg             -0.14    0.91   -0.66
...
```

During training, backpropagation calculates gradients for the rows used in each batch, and the optimizer adjusts their values to reduce the model's loss. If two categories play similar roles in predicting sales, their vectors may move closer together in the learned embedding space.

The model isn't given these relationships explicitly. It discovers task-specific associations from patterns in the training data, which means we shouldn't assume that an embedding captures every real-world relationship—or even that every relationship it captures will generalize beyond the task.

The Rossmann paper offers a striking example. The authors learned six-dimensional embeddings for the 12 state categories, then used t-SNE to project those vectors into two dimensions. The resulting visualization looked surprisingly similar to Germany's geography. It even placed the eastern states of Saxony, Thuringia, and Saxony-Anhalt in the same cluster. The authors suggested that neighboring states may share economic and cultural patterns that also affect store sales.

There is an important limit to that interpretation. The model learned to predict sales, not geography, and the plotted coordinates came from a nonlinear t-SNE projection rather than directly from two embedding dimensions. The result shows that useful structure can emerge from learned embeddings. It does not show that embeddings will always recover geography—or any other real-world relationship we hope to find.

### Other Benefits

Embeddings have another useful property: they turn categorical values into dense, continuous representations that the model can refine during training. Instead of treating each category as an isolated label, the model gets a set of numerical features it can learn from.

We can then concatenate those embeddings with genuinely continuous variables and feed the combined values into the same model. This allows the model to learn interactions between both kinds of data. _Deep Learning for Coders with fastai and PyTorch_ points to Google Play's app recommendation system as one example of this approach at the time the book was published.

## Keep It Simple

Many machine learning courses open the fire hose: they introduce a long list of algorithms, briefly explain the mathematics behind each one, and follow up with a small worked example. That breadth can be informative, but it can also make us lose sight of the question that matters most in practice: when should we use each approach?

The book offers a useful rule of thumb: "The vast majority of datasets can be best modeled with just two methods."

1. **Ensembles of decision trees** work well with structured data, including the kinds of tables we often encounter inside a company.
2. **Multilayer neural networks trained with SGD** work well with unstructured data such as audio, images, and natural language.

We've already spent plenty of time on deep learning, so what makes decision trees worth considering?

1. They usually train faster.
2. Their predictions can be easier to interpret.
3. They can run efficiently on CPUs, without requiring GPU acceleration for inference at scale.
4. They often require less hyperparameter tuning.
5. They belong to a mature ecosystem with well-established tools and techniques.

Taken together, these advantages make an ensemble of decision trees a sensible first approach for a new tabular dataset. It isn't an absolute rule, though. A neural network may be a better starting point when:

1. The data contains very high-cardinality categorical variables, such as a `zip_code` column with many possible values.
2. Some columns contain unstructured data that a neural network can understand more naturally, such as the text from a meeting transcript.

Real-world datasets won't always fit neatly into one category. When the choice isn't obvious, follow the same advice this course has emphasized throughout: try more than one approach and optimize for quick iteration. Look for early evidence that a method is promising, and don't be afraid to move on when it isn't.

## 2. Handle ordinal columns

An _`ordinal`_ column refers to a column that generally contains string info (but not always) that can be represented in a natural order that is not already facilitated by the datatype. What we mean by that is that a column like `rating`, which is 1-5, _can_ be ordinal, but since it's numerical, the order or ranking is already implicitly handled. Whereas a column like `ProductSize` might contain:

```python
df['ProductSize'].unique()
```

```text
array([nan, 'Medium', 'Small', 'Large / Medium', 'Mini', 'Large', 'Compact'], dtype=object)
```

In this case, we as humans understand that there is an organic order to these strings, but a model likely has no way to differentiate the relationship or order between `Small` and `Mini`. We can help this differentiation along by being a little more explicit -- aka "handling ordinal columns."

```python
sizes = 'Large','Large / Medium','Medium','Small','Mini','Compact'
df['ProductSize'] = df['ProductSize'].astype('category')
df['ProductSize'].cat.set_categories(sizes, ordered=True, inplace=True)
```

## 3. Identify the dependent variable

This might seem obvious, but we need to look at the data and ask ourselves, "What are we trying to predict?" What is the column or value that we are looking to derive based on all the other data points available to us? For our example, the dependent variable is pretty obvious and straightforward. We are looking to predict the `SalePrice`. But there may be applications where the dependent variable could be one of a handful of seemingly valuable data points, and the overall goal is to determine which data point helps deliver the most value.

## 4. Choosing a good metric

Now that you know what you want to predict (from #3), the next challenge will be determining _how_ you are going to measure the effectiveness or accuracy of said predictions. Basically, how do you know if your model is doing a good job of making predictions, and how accurate are those predictions?

This is a very important step and really should not be taken lightly. You can train your model until the cows come home and spend hours of CPU cycles doing so -- but if you don't have clarity from a data science standpoint about _how_ you are going to measure the performance of your model and, frankly, _when_ you can consider training to be done, you're likely going to waste a lot of time and energy without really building conclusions from a place of confidence. Unless you've taken the time to sit down and _design_ the metrics you will use to measure success, you've basically taken a more roundabout way of "guessing." Until you know how to accurately measure what makes one prediction "good" versus another, it's data science done with a shrug.

# Decision Trees
If we are going to implement decision tree ensembles in our algorithm, we should probably understand the basics of how a decision tree works and what a typical training cycle would look like.

A decision tree asks a series of binary questions about the data or values derived from the data. For example, "age < 30?" or "high income?"

A sequence of such questions can help "sift" our data into groups. A "yes" here and a "no" there, asked of each row, causes our data to "plinko" and settle into groups.

But what good is this? If the whole goal was to make a prediction, what good does sifting our data into groups do? We haven't made any sort of prediction or landed at some predictable value. All we've done so far is place "like" rows into the same groups based on a sequence of binary questions.

The value is that a predicted value can be assigned to _each_ of the groups -- and there are a lot of techniques for doing this, but for simplicity, we will take the target mean of the items in the group. AKA the average sale price.

The objective is to identify the series of questions that will help break our data into progressively "better" groups. We use the average sale price of each group as the "prediction" and see how it compares to the actual observed sale prices in the group.

Some "questions" will be better at breaking groups along clean "seams" where the predictions are very close -- others will not be as valuable. For example, `ModelYear` might be a much better seam to use than `Color` when determining which question will group items with an average sale price closer to the actual observed prices.

So, that's the theory -- and the machine learning comes from the programmatic approach we can take with our dataset to arrive at the best tree to build. AKA we can use machine learning to identify the highest-value binary questions and progressively build our tree from them, giving us the best shot at making an accurate prediction.

## The basic steps (formalized)
```text
1. Loop through each column of the dataset in turn.
2. For each column, loop through each possible level of that column in turn.
3. Try splitting the data into two groups, based on whether they are greater than or less than that value (or if it is a categorical variable, based on whether they are equal to or not equal to that level of that categorical variable).
4. Find the average sale price for each of those two groups, and see how close that is to the actual sale price of each of the items of equipment in that group. That is, treat this as a very simple "model" where our predictions are simply the average sale price of the item's group.
5. After looping through all of the columns and all the possible levels for each, pick the split point that gave the best predictions using that simple model.
6. We now have two different groups for our data, based on this selected split. Treat each of these as separate datasets, and find the best split for each by going back to step 1 for each group.
7. Continue this process recursively, until you have reached some stopping criterion for each group—for instance, stop splitting a group further when it has only 20 items in it.
```


The goal is to find the sequence of questions that will give us the best "splits" in our data.

With these concepts in mind we are _almost_ ready to begin training, but there are a few more data specific items we should address. Some of them are mandatory and others are nice steps to really give our prediction model the best shot at making accurate predictions.

# Handling Dates
This is the first "nice to have" bit of data preparation, and it specifically pertains to how our model will treat and interpret dates. Remember that the fundamental mechanism behind a decision tree is _bisection_, or splitting our data into groups based on some criterion. That criterion can depend on the underlying data type of the column in question. When the value is `ordinal`, we can divide based on whether the variable's value is greater than (or less than) a threshold. When the value is `categorical`, we can divide the data based on whether the variable is at a particular level.

But how does this sort of logic apply to a more conventional data type like a `date`? Dates are interesting in that they can represent `ordinal` values ("January comes before February"), but they also contain a lot of implicit qualities that the simple act of placing them in order can miss. We might want to incorporate some of this nuanced behavior into our model as well. Take, for example, the difference between Black Friday and any other arbitrary shopping day. Order alone might not capture that a given date is a commercial holiday, so we may want to give our model some additional information to work with.

All of this is to say -- we are leaving a lot of valuable data on the table if we treat dates purely as `ordinal` values. Thankfully, the `fastai` library gives us an easy way to supplement `date` data with additional metadata (by way of additional columns). This can help our tabular models really "understand" and start to leverage the valuable information that can be gleaned beyond the simple sequence of dates within a given calendar year.


```python
df = add_datepart(df,'saledate')
```

Then you can observe all of the nice additional columns that were added to the original data frame.

```python
' '.join(o for o in df.columns if o.startswith('sale'))
```
```text
'saleYear saleMonth saleWeek saleDay saleDayofweek saleDayofyear saleIs_month_end saleIs_month_start saleIs_quarter_end saleIs_quarter_start saleIs_year_end saleIs_year_start saleElapsed'
```

This is a very simple and high-impact step to take when you are working with tabular data and some of the data points happen to incorporate dates. Don't overlook the opportunity to introduce some more "real-world" behavior (indirectly) by enriching your date data with some nice metadata.

# Using TabularPandas and TabularProc
We won't spend too much time on this specific topic, but the reality is that real-world datasets will be incomplete, especially when it comes to certain columns and data types.

Before we use the dataset for training, we have to preprocess it so that it is ready to be ingested by our model. This includes:

1. translating categorical data into numerical codes
2. filling in missing continuous values in a meaningful way that will not cause our model to crash or produce confusing results

We can accomplish both of these tasks with the help of some `fastai` creature comforts provided by `TabularPandas`.

The long and short of it is that `TabularPandas` is a DataFrame-like wrapper around our existing data (our actual data) that allows us to more easily transform the underlying values. This is done via "procs" (transformers) called `TabularProc`s. The gist is that we are using some tooling the `fastai` API has on offer to get our data into a place where it is ready for training.

* `Categorify` allows us to assign numerical category codes to string representations.
  - Conceptually: Small --> 0, Medium --> 1, Large --> 2 ... although the exact codes are learned from the data.
* `FillMissing` replaces missing values in continuous columns using a fill strategy (the median by default). It can also add a Boolean column that records which values were originally missing.
